## Question

Specify a build-time map-baking generator, mirroring `vendor/atlas-builder` → `atlas.odin`: it reads the authored `data/maps/*.json` files (the [Map type and persistence](01-map-type-and-persistence.md) ticket's `Map`/`load_map` format) and emits a generated Odin source file containing a `Map_Name :: enum {...}` (one case per map file, exactly mirroring `Texture_Name`'s shape) indexing a fully-baked `[Map_Name]Map` table — literal Odin composite-literal data, not embedded raw JSON parsed at runtime, since map data (unlike image bytes) needs no decode step.

This blocks the [map-selection screen](02-map-selection-screen.md): Playing mode's map discovery becomes "enumerate `Map_Name`" rather than a runtime directory scan, and `game.current_map` gets populated by copying out of the baked table rather than calling `load_map` on a file path.

Needs to settle:

- **Tool structure and wiring.** Does this live in its own `vendor/map-builder/` (mirroring `vendor/atlas-builder`), invoked as a new `build.sh` step before the game build (`odin run vendor/atlas-builder` → `odin run vendor/map-builder`), generating a new root file (e.g. `maps.odin`, with the same "This file is generated by running the map_builder" header comment atlas.odin uses)?
- **`Map_Name` derivation.** One enum case per `data/maps/*.json` file — confirm the naming convention (filename `desert_dungeon.json` → enum case `Desert_Dungeon`, mirroring `Texture_Name`'s casing) and what happens if a filename doesn't cleanly title-case.
- **Deep-copy at instantiation.** [Ticket 1](01-map-type-and-persistence.md)'s Answer flags that copying a `Map` value only copies its `[dynamic]Tile`/`[dynamic]Spawner` slice headers, aliasing the shared baked table's backing memory unless an explicit deep copy happens. The selection screen must call ticket 1's `clone_map` (or equivalent) when instantiating `game.current_map` from `MAPS[chosen]` — pin down exactly where that call happens and confirm no other path reads from `MAPS` directly without cloning.
- **Editing mode stays file-based.** Confirm explicitly: Editing's own map switcher ([ticket 3](03-editor-map-switcher.md)) keeps reading/writing the live `data/maps/*.json` files via `load_map`/`save_map` — it never touches the baked `MAPS` table, which only Playing mode consumes. This means editing and saving a map does *not* show up in Playing until the generator re-runs and the executable rebuilds (a step beyond the earlier "stale until relaunch" call — now "stale until rebuild"). Confirm this workflow tradeoff is accepted, noting it matches the existing texture/atlas workflow (editing `data/textures/*.aseprite` already requires an atlas-builder + rebuild cycle before changes appear in-game).
- **What the generator does with `Map.name`.** Since `Map` now carries a display `name` distinct from the filename, confirm the generator reads it straight out of each JSON file's `name` field into the corresponding baked literal, with no separate naming step.
- **`map_path_for_name` proc.** [Ticket 3](03-editor-map-switcher.md)'s resolution needs a `map_path_for_name :: proc(name: Map_Name) -> string` (the inverse of `Map_Name` derivation above: enum case → `data/maps/<slug>.json` path) for the in-editor map switcher and its `editing_map_path` tracking, which never reads the baked table and always needs a real file path. Emit this alongside the generated `Map_Name` enum, using the exact same naming convention.

## Answer

**Tool structure and wiring.** New `vendor/map-builder/`, mirroring `vendor/atlas-builder`'s shape as a standalone Odin program. New `build.sh` step, run before the game build and after the atlas step:

```bash
echo "== Building atlas =="
odin run vendor/atlas-builder -out:build/atlas-builder.bin

echo "== Building maps =="
odin run vendor/map-builder -out:build/map-builder.bin

echo "== Building and running game =="
odin run . -out:build/shooter.bin
```

Generates `maps.odin` at the repo root, with the same `// This file is generated by running the map_builder.` header comment style atlas.odin uses.

**`Map_Name` derivation.** One enum case per `data/maps/*.json` file, using the exact same call atlas-builder already uses for `Texture_Name` (atlas_builder.odin:248): `strings.to_ada_case(slashpath.name(slashpath.base(path)))` — `desert_dungeon.json` → `Desert_Dungeon`. No bespoke casing rule; whatever `to_ada_case` produces for a given filename is the case name, same as textures today. Map authors are expected to name files the same way texture/aseprite source files already are (snake_case, valid-identifier-ish) — not a new constraint this effort introduces.

```odin
Map_Name :: enum {
	Desert_Dungeon,
}
```

**Generated table shape.** A package-level var with a composite-literal initializer, matching `atlas_textures`'s exact shape (atlas_builder.odin:1131) — not a true compile-time constant, since `Map`'s `[dynamic]Tile`/`[dynamic]Spawner` fields need runtime allocation regardless of who constructs them:

```odin
maps: [Map_Name]Map = {
	.Desert_Dungeon = Map{
		name = "Desert Dungeon", // read straight from the JSON file's `name` field
		player_start = {...},
		tilemap = Tilemap{tile_size = {16, 16}, tiles = {Tile{...}, ...}},
		spawners = {Spawner{...}, ...},
	},
}

// data/maps/<Map_Name-derived-slug>.json, for callers that need the live file
// path rather than the baked table (the editor's switcher, ticket 3)
map_path_for_name :: proc(name: Map_Name) -> string {
	switch name {
	case .Desert_Dungeon: return "data/maps/desert_dungeon.json"
	}
	return "" // unreachable: name is always one of the above
}
```

**Deep-copy discipline.** The [map-selection screen](02-map-selection-screen.md) is the *only* call site that reads `maps[chosen]`, and it does so through `clone_map` (ticket 1) immediately, before assigning to `game.current_map`:

```odin
game.current_map = clone_map(maps[chosen_map_name])
```

Nothing else in the codebase reads the `maps` global directly — Editing mode never touches it at all (ticket 3 is exclusively file-based via `load_map`/`save_map`/`map_path_for_name`).

**Editing mode stays file-based; "stale until rebuild" accepted as-is.** Confirmed: editing and saving a map (ticket 3) never touches `maps` or `maps.odin` — only `data/maps/*.json`. Seeing those changes in Playing requires re-running `vendor/map-builder` and rebuilding, exactly the same discipline `data/textures/*.aseprite` already imposes via `vendor/atlas-builder`. No dev-mode fallback (e.g. a runtime flag that reads live JSON instead of the baked table) is in scope for this effort.

**`Map.name`.** Read straight from each JSON file's `name` field into the corresponding baked literal — no separate naming or derivation step, unlike `Map_Name` (which is derived from the filename, not the JSON content).
