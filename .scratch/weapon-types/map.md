Label: wayfinder:map

## Destination

An implementation-ready spec for a player-only multi-type weapon system: Gun keeps today's clip/reserve/reload mechanic, Melee swings (with cleave), and Magic casts via generic plumbing for future spell effects. The player always has exactly one weapon equipped.

**Redrawn 2026-08-23** (see [ADR-0002](../../docs/adr/0002-class-locked-weapon-acquisition.md)): weapon type is no longer acquired via a random enemy-dropped pickup. Instead, the player picks a Class (Melee/Magic/Ranged) once at game start, permanently locking which weapon family they can ever equip; progression within that Class runs on Gold earned from kills, spent in an on-demand Shop to buy up a fixed tier ladder of `Weapon_Kind`s, each purchase replacing the current weapon outright. "Done" still means a build session could implement this directly with no open design questions left.

## Notes

- Codebase: Odin + raylib. Single global `game` struct, free-function updates (`update_x`/`draw_x`), no OOP/classes. Enums + `[Enum]T` preset tables are the existing idiom (`weapon_presets`, `pickup_texture_names`).
- Established polymorphism pattern to mirror: `Enemy_Behaviour :: union { Melee, Ranged }` dispatched via `switch &b in enemy.behaviour` (enemy.odin). The new `Weapon` should follow the same shape: tagged union, common header + per-variant payload.
- Key files: `weapon.odin` (Weapon/reload/fire), `bullet.odin` (Bullet, `fire_pellets`, `update_bullets`, hit detection/damage/particles), `main.odin` (Player struct, save/load via `core:encoding/json`, input glue), `pickup.odin` (`Pickup_Kind`, `collect_pickup`), `hud.odin` (ammo/reload UI).
- `Player.weapon` has no `json:"-"` tag — it's persisted to `data/game_save.json` as run progression (like `xp`/`level`). This makes the union-decode-order gotcha noted at enemy.odin:23-32 a real risk for the new `Weapon` union, not just a low-stakes editor-template concern.
- When resolving a ticket, call the Skill tool for "grilling" (default). Call "prototype" for tickets marked `Type: prototype`. Call "domain-modeling" too if a ticket's answer is worth recording as an ADR or changes established terminology.

## Decisions so far

- Destination and scope locked via grilling session (2026-08-23): implementation-ready spec, player-only, single equipped weapon (no inventory), `Weapon` becomes a tagged union mirroring `Enemy_Behaviour`, fixed presets per instance, weapon-swap via enemy-dropped pickup (old weapon discarded), Melee/Magic are cooldown-only (no stamina/mana), melee hit detection is an once-per-swing arc/cone check with cleave reusing the bullet damage/particle pipeline, Magic locks only cast plumbing (effects are fog), save persistence needs a real decode guard (not just variant ordering), upgrades apply generically via the common header, `Fire_Mode` (semi/auto cadence) moves to the common header, HUD/visuals are speced at requirements level only.
- [01-weapon-save-decode-safety](issues/01-weapon-save-decode-safety.md): `Weapon` must never be passed directly to `json.marshal`/`json.unmarshal` — persist through a separate non-union `Weapon_Save` DTO (`kind` enum + one `Maybe(_)` payload per variant), converting explicitly at save/load. `Weapon` itself stays a real union at runtime. Confirmed against the local Odin stdlib source (`core:encoding/json`, build `ea5175d`); full evidence and code sketch in the linked findings file.
- [02-weapon-union-shape](issues/02-weapon-union-shape.md): `Weapon` is a wrapper struct (common header: `kind`/`fire_mode`/`damage`/`action_rate`/`cooldown_timer` directly on it) plus a `variant: union { Gun, Melee_Weapon, Magic }` field — not a bare union like `Enemy_Behaviour`, because Odin unions need a switch to read any field and two call sites read header fields directly. Recorded as [ADR-0001](../../docs/adr/0001-weapon-wrapper-struct.md) and in [CONTEXT.md](../../CONTEXT.md). `fire_rate`→`action_rate`, `try_fire_weapon`→`try_use_weapon` (dispatches to per-variant procs returning bool). `Weapon_Kind` stays one flat enum across all types. Full proc shapes (`weapon_create`/`update_weapon`/`try_use_weapon`) in the ticket.
- [03-melee-combat-design](issues/03-melee-combat-design.md): Melee hit-check resolves **instantly** (synchronously inside `try_swing_melee`, no active-frame window, no extra runtime flag needed) using an **arc/cone** hitbox (`dist <= range && angle_to_enemy <= arc/2` around `aim_dir`, mirroring `Gun.spread_angle`'s cone idea). Cleave hits every enemy in the arc via a newly-shared `apply_hit_to_enemy` proc factored out of `bullet.odin`'s inline pipeline, reused by both bullets and melee. Validated via an interactive prototype — [prototypes/03-melee-swing.html](prototypes/03-melee-swing.html).
- [04-magic-plumbing-design](issues/04-magic-plumbing-design.md): `try_cast_magic` resolves **instantly/synchronously** (same contract as `try_swing_melee`/`try_fire_gun`) — any persisting effect (projectile, AoE, DoT) is its own tracked entity later, not state on `Weapon`/`Magic`. `Magic :: struct {}` stays empty for now; no `Spell_Kind` enum yet, added by the future spell-effect ticket once there's an actual list to enumerate. Dispatched from the existing `switch &v in weapon.variant`, no new pattern introduced.
- **Destination redrawn** (2026-08-23, [ADR-0002](../../docs/adr/0002-class-locked-weapon-acquisition.md)): weapon acquisition is no longer a random enemy-dropped pickup. The player picks a Class (Melee/Magic/Ranged) once at game start, permanently locking their weapon family; progression runs on Gold spent in an on-demand Shop against a fixed per-Class tier ladder. [05-weapon-pickup-integration](issues/05-weapon-pickup-integration.md) closed out of scope as a result.
- [08-class-selection-mechanics](issues/08-class-selection-mechanics.md): Class is picked once ever (no run-reset — `Restart` already leaves weapon/XP/level untouched, Class follows suit) via a new `ProgramMode.Class_Select` (not a boolean modal — avoids a placeholder weapon existing before Class is chosen). All three Classes offered now, including Magic despite it having no real content yet (explicit user call, accepted as a known gap).
- [09-gold-pickup-mechanism](issues/09-gold-pickup-mechanism.md): Gold is a new `.Gold` `Pickup_Kind`, reusing all existing pickup machinery, folded into the same uniform 3-way `rand.choice_enum(Pickup_Kind)` roll at the existing `PICKUP_DROP_CHANCE` — no special-cased odds needed for a steadily-accumulating currency.
- [10-weapon-shop-and-tier-ladder](issues/10-weapon-shop-and-tier-ladder.md): a dedicated on-demand Shop panel (not tied to XP level-ups) sells a fixed sequential per-Class tier ladder of `Weapon_Kind`s; buying immediately equips and discards the old weapon outright, no unlocking/switching back. Coexists with, doesn't replace, ticket 06's XP-level-up generic upgrades. `Weapon_Kind` stays flat; Class-bucketing is a new lookup table, as ticket 02 anticipated.
- [06-generic-upgrade-system](issues/06-generic-upgrade-system.md): `upgrade_weapon` splits into an unconditional header pass (`damage`/`action_rate` multipliers, all variants) plus a `switch` for the Gun-only clip bonus, with `Melee_Weapon, Magic` left as an empty placeholder case. The level-up modal conditionally renders — Gun keeps all three buttons, Melee/Magic drop "Refill Ammo" (no ammo-equivalent resource) down to just "Upgrade Weapon"/"Skip". `refill_weapon_reserve` narrows to take `^Gun` directly.
- [07-hud-and-visual-requirements](issues/07-hud-and-visual-requirements.md): HUD row 3 switches on `weapon.variant` (Gun keeps today's ammo/reload row; Melee/Magic get a cooldown-readiness row reusing `weapon_texture_names[kind]` as the icon). Gold gets its own corner readout, not a bar-stack row. `draw_weapon` requirements: melee gets a cosmetic rotation sweep over `swing_time`, magic gets a particle cue on cast (exact look stays fog). Shop shows "Fully Upgraded" at max tier; `Class_Select` shows label + one-line description per Class, no icon yet. **Last open ticket — the map's route is clear.**

## Not yet specified

- The actual list of Magic spell effects (projectile, homing, AoE, DoT, etc.) — each is its own design question once the Magic plumbing (see ticket 04) exists.
- Concrete named `Weapon_Kind` content for the Melee and Magic tier ladders (Ranged already has Pistol/SMG/Shotgun) — names, stats, and per-tier Gold prices are content-authoring, not mechanism design (ticket 10 locked the mechanism only).
- At least one placeholder Magic `Weapon_Kind` with real header stats (damage/action_rate/cooldown) needs to exist before Magic is actually playable as a Class — its cast stays a no-op (ticket 04) until spell effects land, but Class_Select can't hand a Magic-picking player a weapon that doesn't exist in `weapon_presets`.
- Type-specific upgrade paths beyond the generic damage/cooldown upgrades (e.g. wider melee arc, extra magic effect radius) — follow-on tickets once each type is implemented.
- Concrete animation curves / sprite work for melee swings and magic casts, beyond the display/behavior requirements captured in ticket 07.
- Shop panel's exact open-trigger (which key/button) and Class_Select's exact layout — left to the build session as UI polish, not a design branch.
- What (if anything) Gold does once a Class's tier ladder is maxed out — no sink beyond the ladder is speced; surfaced while locking the Shop panel's max-tier display (ticket 07).

## Out of scope

- Multi-weapon inventory/carrying and switching between several simultaneously-held weapons — the player has one equipped weapon at a time. Would return as a fresh effort if this destination were redrawn.
- Unifying player weapons with the enemy `Enemy_Behaviour` system — enemies keep their own separate, already-working Melee/Ranged behavior.
- A mana/stamina resource economy for Melee/Magic — this first cut is cooldown-only; an economy layer is a separate future effort.
- A true roguelite "run" structure (Class re-picked, Gold/weapon/XP reset on death) — considered and rejected while designing Class selection (ticket 08); today's `Restart` stays a soft reset (heal + clear battlefield only), matching the pre-existing model. Would return as a fresh effort if this destination were redrawn again.
- Random cross-type weapon-swap pickups — the original mechanism ticket 05 was designing before the destination was redrawn ([ADR-0002](../../docs/adr/0002-class-locked-weapon-acquisition.md)); superseded by Class-locked acquisition, not merely deprioritized.
