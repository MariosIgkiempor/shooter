# In-game menus drop nine-slice and vendor/ui for a flat-rect, Reveal/Dismiss-animated component set

Status: accepted

Supersedes [ADR-0010](0010-hand-rolled-menu-ui-no-layout-engine.md): its "no generic layout engine, hand-rolled component set" decision stands, but its "reuse `draw_nine_slice` for panel backgrounds" line is overturned. The six in-game menu Screens move to flat-rectangle panels/buttons (fill + a 2px accent border, no shadow) and every Menu element gets a Reveal (fade-in, scale 0.9→1.0) / Dismiss (reverse) driven by `ease_out_cubic` over 0.20s, validated live via a throwaway prototype (`prototype/menu-ui-polish` branch; see [Prototype flat-rect visual style + Reveal/Dismiss motion feel](../../.scratch/menu-ui-polish/issues/01-prototype-flat-rect-visual-and-motion.md)). A Screen change (switching among Splash/Main_Menu/Run_Start/Map_Selection/Shop/Run_End — unifying `program_mode`/`run_ended`/`shopping`) now goes through one chokepoint, `request_screen_change`, which defers the actual state write until the outgoing Screen's Dismiss finishes: direct assignment to `program_mode`/`run_ended`/`shopping` at any existing call site can no longer play a Dismiss, since the old screen stops drawing the instant its underlying field flips.

Reveal/Dismiss timer state is **not** per-element: a single shared transition record (current Screen, when its Reveal began, and — only while a Screen change is in flight — its Dismiss start time and target) is enough, since every element's alpha/scale is a pure function of elapsed time plus its ordinal rank, validated by the prototype needing no per-element mutable state. Rank also drives staggering: Main Menu's four buttons cascade (reveal in order after the panel, dismiss in reverse before it closes last) as the map's one worked stagger example; every other screen uses rank 0 throughout (synchronized, no stagger), per the map's explicit scope boundary against choreographing all six screens individually.

Considered Options: each screen owning its own "pending dismiss" flag instead of one shared `request_screen_change` chokepoint (rejected — a deferred-transition mechanism is pointless if call sites can still bypass it, and centralizing it means every future Screen change gets Dismiss for free); a named per-screen state struct with one field per animated element (rejected — the prototype proved elapsed time + rank sufficient, so per-element fields would be unused complexity); extending the new unified Screen concept to replace every `program_mode`/`run_ended`/`shopping` check across the codebase (rejected — scoped narrowly to the menu-drawing/transition code, since gameplay logic elsewhere has no need for it).

See [Flat-Rect Menu UI: Transitions & Animation](../../.scratch/menu-ui-polish/map.md) and [Component API & Reveal/Dismiss state model](../../.scratch/menu-ui-polish/issues/02-component-api-and-state-model.md) for the full spec this settles.
