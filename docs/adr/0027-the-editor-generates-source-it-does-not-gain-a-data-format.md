# The editor generates source, it does not gain a data format

Status: accepted

[ADR-0020](0020-enemy-kind-is-the-authored-unit.md) made `Enemy_Preset` a code table on the `weapon_presets` model, and [Enemy variety model](../../.scratch/content-expansion/issues/01-enemy-variety-model.md) collapsed a Map's composition entry to `(kind, count)` — which deleted the editor's per-entry tuning sliders, the only place an enemy's speed, wobble, damage, range and cooldown could be moved without a rebuild ([editor.odin:694](../../editor.odin)). Those sliders worked because they wrote into a composition entry's own template copy, which `save_map` persisted into the map file. A slider pointed at a code table has nowhere to save to, so the tuning surface dies with the field it edited.

**The editor keeps a tuning surface — its own mode, editing the live `enemy_presets` — and persists by writing the Odin literal, not by loading one.** `enemy.odin` stays the single authoritative roster; the editor exports into it.

The obvious alternative is to move `enemy_presets` into a data file the editor reads and writes, the way it already reads and writes maps. It was rejected on two grounds. First, it undoes the move [ADR-0020](0020-enemy-kind-is-the-authored-unit.md) made: the reason a Composition names a kind and nothing else is that a kind is the same enemy wherever it appears, and a roster that ships as loadable data is a roster a build can disagree with. Second, and decisively, it hands the roster back to `core:encoding/json`'s union-variant guessing — confirmed broken in this repo, where a `Kills_Reached`/`Repeating` trigger round-tripped back as `Time_Elapsed(0)`/`One_Shot`, silently — and [Boss model](../../.scratch/content-expansion/issues/05-boss-model.md)'s phase rotation is a slice of `(attack, tell seconds)` pairs inside an `Attack_Style` variant, which is precisely the nested-union shape that breaks. Generating source sidesteps the marshaller entirely. The third option, tuning in memory and copying numbers out by hand, keeps the code table but throws away the surface the sliders provided, which is the thing being preserved.

Consequences: the export is one-directional, so a tuning session shows up as a reviewable diff to `enemy.odin` and the roster stays in git rather than in a file nobody reviews. Nothing at runtime can load a roster no build has seen. `vendor/map-builder`'s `write_*_literal` procs are the established precedent — generating Odin source from authored data is already how maps reach the binary — so this adds a second generator rather than a second idiom. The costs are a bake round trip (a tuned number is not live until the next build, the same lag a new map file already has) and a generator that must stay in step with `Enemy_Preset`'s shape, which is the standing tax on every literal writer in `map_builder` already. The panel gets its own `EditorMode` rather than joining the always-visible column: presets are global and shared by every Map, so editing one from inside a particular map has nothing to do with that map, and the always-visible column should not become where everything lands by default.

_Amended._ The literal lives in its own generated file, `enemy_presets.odin`, rather than inside `enemy.odin` as written above. Two reasons, found on building the mode: a regenerated literal cannot carry the per-row design comments the hand-written table had grown, so those moved onto `Enemy_Kind`'s cases and the table became a file with no prose to lose; and a whole file is a target a test can pin — `enemy_presets_source_test` asserts the checked-in file is byte-for-byte what the generator writes for the live table, which is what keeps "the generator must stay in step with `Enemy_Preset`'s shape" a failing test rather than a broken Export. The substance stands: the roster is source, the editor exports into it, and nothing loads it. One consequence above was too pessimistic — the table is a mutable global, so an edit *is* live in the running session (the next spawn stamps it); only persisting it needs the bake. The two per-Kind Tunables that had bridged the gap (`max_health`, Gold) are gone for the reason the rejected alternative was: a Tunable over a preset is a path by which `Save Tuning` persists the roster as data.
