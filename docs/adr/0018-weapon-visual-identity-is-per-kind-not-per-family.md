# Weapon visual identity is per-kind, not per-family

Status: accepted

Amends the art-revamp effort's [ticket 02](../../.scratch/art-revamp/issues/02-weapon-shape-and-reconcile-weapon-action-feel.md) decision, which locked "distinct silhouette per weapon **family** (Gun=rod, Melee=wedge, Magic=rod+orb)". Each of the eight `Weapon_Kind`s now gets its own silhouette, in the UI **and** in the world: Pistol, SMG and Shotgun are three visibly different objects, not three uses of one rod. Weapon *effects* (muzzle flashes, swing trails, the streak/flash particle vocabulary) keep their per-family **shapes** and vary only in **magnitude** per kind — a smaller flash for a Pistol than a Shotgun — so weapon-action-feel's effect design is retuned, not reopened.

The rejected position was that icons could be per-kind while the world stayed per-family, on the grounds that a 20x5px rod rotating with aim can't carry eight distinctions mid-combat. That is a real constraint, and it is answered by *how* the eight differ rather than by dropping to three: distinctions are **countable** (one barrel vs. two, one orb vs. three, blade + guard + pommel), never proportional, because you cannot compare a 20px rod to a 24px rod with no reference alongside it but you can count barrels at any size. Weapons also grow to roughly 1.5x their previous size to make room, with the actor's own footprint as a soft ceiling. An icon promising a distinction the world then refuses to honor is the failure this avoids — it would mean buying a Shotgun icon you never see again.

Both halves come from one unit-space geometry definition per kind, with two thin adapters: an icon adapter mapping it into a destination `Rect`, and a world adapter running it through `draw_weapon`'s existing pivot/angle/pulse transforms. Authoring the two separately would let a Shop icon and the thing in your hands drift apart on the first tweak, which is precisely the problem per-kind identity exists to solve.

Per-kind visual parameters are **derived from `Weapon_Kind` at draw time, never stored on `Weapon`**. `Weapon` is serialized into `data/game_save.json`, so a stored copy would bake art into save data — a player who saved before a retune would keep the old silhouette, and a save predating the fields would decode them as zero, yielding an invisible weapon with no error. This follows [ADR-0007](0007-upgrade-stacks-recomputed-not-mutated.md)'s recompute-don't-mutate principle and matches what `draw_weapon` already does with the melee wedge, whose drawn length reads the live upgrade-scaled `Melee_Weapon.range`. A future Upgrade that scales weapon size therefore needs no re-sync step: it becomes another multiplier in the same draw-time expression, alongside the global scale multiplier exposed as an F8 debug-panel slider for tuning in motion.

Considered Options: keeping per-family silhouettes and accepting that the Shop can't distinguish tiers visually (rejected — the Shop is exactly where a player chooses between them); per-kind icons over per-family world art (rejected as above); per-kind effect *shapes* as well as magnitudes (rejected — a muzzle flash is a ~100ms transient nobody reads as identity, and eight effect treatments would need judging in motion as an effort of their own); storing visual parameters on `Weapon` with `json:"-"` (rejected — if a value is always derivable from `kind`, an instance copy only creates a way for it to be wrong).

Implemented in two passes: UI icons first ([icon.odin](../../icon.odin)), world silhouettes and the debug slider second, since world shapes can only be judged at gameplay zoom in motion.
