# Persisted enums are stored by identity string

Status: accepted

Every enum this game wrote to disk went out as a bare ordinal. `core:encoding/json` marshals an enum as its integer value unless `use_enum_names` is passed, and nothing passed it — so `data/game_save.json` held `"kind": 0` for the player's weapon and `data/maps/desert_dungeon.json` held `"kind": 0`/`1`/`2` for its four spawn discriminants. That made *declaration order* a persistence contract nobody declared: inserting a `Weapon_Kind` above another, or sorting `Movement_Style_Kind` alphabetically, silently rewrote the meaning of every saved file that referred to it. [CONTEXT.md](../../CONTEXT.md)'s Account progression entry had already noticed the hazard for one enum — cleared Maps are keyed by Map identity "because `Map_Name` is generated in filename order" — and [map.odin](../../map.odin)'s `map_identity_string` was the one-off fix.

**Every persisted enum value is written as its own case name, and a name no case carries is a load failure the reader reports.** One parametric pair in [persistence.odin](../../persistence.odin) — `enum_identity_string` / `enum_from_identity_string` — is the only conversion, and the one-off `map_identity_string` collapses into it. A persisted enum is a plain `string` field on the wire: the five `*_Save` discriminants change type, and `Weapon.kind`, `Weapon.fire_mode` and `Magic.spell_kind` keep their enum types for the many sites that read them but gain a `json:"-"` tag and an identity-string sibling, the same shape `Weapon.variant`/`Player.weapon_variant_save` already used.

The obvious alternative — `json.marshal(..., {use_enum_names = true})` — writes the right thing and reads the wrong one. Its read side loops an enum's names and, finding no match, returns `true, nil` and leaves the zero value (`// TODO(bill): should this be an error or not?`, `core/encoding/json/unmarshal.odin`). That is *precisely* the failure this exists to prevent: a renamed case would resolve to whatever now sits at ordinal zero, as silently as the ordinal did. The second alternative, a read path that still accepts an ordinal for one release, was rejected because it keeps alive the exact contract being deleted and, with no version field anywhere in the format, could never be safely removed.

A failed lookup fails the load rather than repairing it. `load_map` returns `ok = false`; `load_game` falls back to `initialize_default_game_state`, the same landing the unmarshal error above it already had. The `*_from_save` procs name the offending identity and its enum, the load path names the file and the record, so between them the log says exactly which edit is needed. The accepted cost is that an unresolvable name in `game_save.json` resets the whole save, account progression included — a real cost, taken because the alternative is a half-loaded save, a concept this codebase does not otherwise have.

Consequences: `data/maps/desert_dungeon.json` was migrated in the same change, and the format break is one-way. `vendor/map-builder` carries a duplicated switch on the same case names as string literals — it cannot import the game package — which extends the standing generator tax [ADR-0027](0027-the-editor-generates-source-it-does-not-gain-a-data-format.md) already names; its unknown-name arm now panics rather than baking `nil`, so a stale map file stops the build instead of producing a Spawn Trigger with no condition that the game simply never fires. Two smaller things fell out. `Weapon_Variant_Kind` gained a `None` case: an unequipped weapon is a real state (`initialize_default_game_state` leaves one behind), the four other `*_to_save` procs already named their nil case, and `weapon_variant_to_save` had been reaching `unreachable()` on it — the string encoding forced the fix by making `""` otherwise ambiguous with a corrupt file. And an identity string read off disk is heap-allocated where an ordinal was not, so `load_map` frees each one once it has resolved it — it unmarshals into a fresh local `Map`, so a non-empty identity there is always heap, and a map switch would otherwise leak one string per trigger and per composition entry. `load_game` deliberately does not: it unmarshals into the long-lived `game`, where a key absent from the file leaves the previous string in place, and that string may be one `enum_identity_string` returned — a pointer into static type info that must never be freed. It runs once per process and leaks at most three small strings, which is the posture the rest of `load_game` already takes toward what `json.unmarshal` allocates for it. `delete_identity_string` takes a pointer and blanks the field so the safe case can't double-free either.
